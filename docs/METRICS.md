# 指标口径文档

> 本文档是 `backend/app/semantic/metrics.yaml` 的可读版本，供面试讲解与团队对齐使用。
> **凡口径有争议的地方，以本文档 + yaml 为准，不以"业界惯例"为准。**

- 数据源：天池 UserBehavior（行为日志，无金额字段）
- 覆盖范围：2017-11-25 ~ 2017-12-03（9 天），**不含双11**
- 统计口径的时间基准：`meta_dataset_range.max_dt`，**不是系统当前日期**
- 时区：固定 `+08:00`（数仓脚本内 `SET time_zone`）

---

## 一、总则：五条不可违反的规则

1. **人数按人去重，笔数按行计数**。两者不可互换，也不可相加。
2. **人数不可跨维度相加**。同一用户一天买 3 个类目，类目表记 3 人，用户表记 1 人；`SUM(类目人数) ≠ 总人数`。
3. **跨天汇总必须重新去重**。把 9 天的日 UV 相加会得到"人次数"，不是"人数"。
4. **相对时间以数据集 `max_dt` 为基准**。用 `CURDATE()` 会查出空集。
5. **金额类指标一律拒答**。数据集只有行为类型，没有价格/金额/退款字段。

## 二、指标清单（25 个）

### 2.1 流量类（原子指标）

| 指标 | biz_name | 定义 | 来源表 | 粒度 | 可用维度 |
|---|---|---|---|---|---|
| 访问人数 | `uv` | 当日有任意行为（pv/cart/fav/buy）的去重用户数 | `dwd_behavior_fact` | dt | dt, category_id, hour |
| 浏览次数 | `pv` | 当日浏览行为次数 | `dwd_behavior_fact` | dt | dt, category_id, hour |
| 成交人数 | `buy_users` | 当日有购买行为的去重用户数 | `dwd_behavior_fact` | dt | dt, category_id, hour |
| 成交笔数 | `buy_cnt` | 当日购买行为次数（笔数近似） | `dwd_behavior_fact` | dt | dt, category_id, hour |
| 加购人数 | `cart_users` | 当日有加购行为的去重用户数 | `dwd_behavior_fact` | dt | dt, category_id, hour |
| 收藏人数 | `fav_users` | 当日有收藏行为的去重用户数 | `dwd_behavior_fact` | dt | dt, category_id |

> `buy_cnt` 的"笔"是**行为次数近似**，不等于支付成功订单数。禁止由此换算 GMV / 客单价。

### 2.2 路径类（依赖 `path_user_session`，本项目差异化资产）

| 指标 | biz_name | 定义 | 过滤条件 |
|---|---|---|---|
| 加购未购人数 | `cart_no_buy_users` | 当日 session 内加购过但未购买的去重用户数 | `has_cart=1 AND has_buy=0` |
| 加购成交人数 | `cart_buy_users` | session 内**先加购、后成交**的去重用户数 | `has_cart=1 AND has_buy=1 AND cart_first_seq < buy_first_seq` |
| 浏览未加购人数 | `browse_no_cart_users` | 浏览商品数达阈值但未加购未成交的去重用户数 | `pv_item_cnt >= 5 AND has_cart=0 AND has_buy=0` |
| 买后加购人数 | `buy_before_cart_users` | session 内先成交、后加购的去重用户数 | `is_buy_before_cart=1` |
| 平均路径长度 | `avg_path_len` | 先加购后成交路径的平均行为条数 | `is_cart_before_buy=1`，`AVG(path_len)` |
| 平均浏览商品数 | `avg_pv_item_cnt` | 加购未购路径的平均浏览商品数（浏览深度） | `has_cart=1 AND has_buy=0`，`AVG(pv_item_cnt)` |

**口径要点：**
- 判定以 **session × 类目** 为单位，跨 session 的"先加购后买"不计入流失。
- `cart_buy_users` 必须带顺序判定。只写 `has_cart=1 AND has_buy=1` 会把"先买后加购"也算进来，口径就错了。
- `buy_users - cart_buy_users` 的差值 ≈ "买后加购"用户，这是路径口径独有的洞察。
- 浏览阈值 5 来自 `business_rules.path_definition.pv_threshold_for_browse`，改配置即可复跑评测。

### 2.3 用户价值类

| 指标 | biz_name | 定义 | 窗口 |
|---|---|---|---|
| 复购人数 | `repurchase_users` | 时间窗内购买次数 ≥ 2 的去重用户数 | 9 天 |
| 高价值用户数 | `high_value_users` | RFM 三要素（R/F/M）均达阈值的用户数 | 9 天 |
| 平均购买笔数 | `avg_buy_times` | 购买用户的人均成交笔数（`AVG(f_times)`） | 9 天 |

**RFM 阈值**（`business_rules.rfm_thresholds`）：

| 维度 | 定义 | 阈值 |
|---|---|---|
| R | 最近一次成交距 `as_of_dt` 的天数 | ≤ 7 天记为高 |
| F | 窗口内成交笔数 | ≥ 2 记为高 |
| M | 窗口内**购买的去重商品数** | ≥ 3 记为高 |

**关于 M 的口径选择（必须能解释清楚）：**
数据无金额，M 用"购买宽度（去重商品数）"近似，而不是直接复用购买次数。
若 M 也用购买次数，F 与 M 的值完全相同，三个打分退化成两个维度，RFM 名不副实。
代价是：M 反映"买得宽"，不反映"花得多"，**面试与文档都必须如实说明**。

**分层规则**（判定顺序即优先级）：

| 分层 | 条件 |
|---|---|
| 高价值 | R=1 且 F=1 且 M=1 |
| 新客 | F=1（仅成交一次）且 R=1 |
| 潜力 | R=1（其余不满足） |
| 流失预警 | R=0 |
| 一般 | 其余 |

RFM 只覆盖 `is_buyer=1` 的用户；零购买用户在 `dim_user` 中以 `is_buyer=0` 单独统计。

### 2.4 留存类

| 指标 | biz_name | 定义 |
|---|---|---|
| 次日留存人数 | `d1_retained_users` | D 日活跃且 D+1 日仍有行为的用户数 |
| 7 日留存人数 | `d7_retained_users` | D 日活跃且 D+7 日仍有行为的用户数（快照列，问单日时不要 SUM） |

**窗口不足时返回 NULL，不返回 0**。最后 7 天没有 D+7 数据，若填 0 会让留存曲线看起来"断崖下跌"，这是 BI 看板最常见的误导。

### 2.5 派生指标（`define_by = METRIC`，只能引用上面已定义的指标）

| 指标 | biz_name | 公式 | 说明 |
|---|---|---|---|
| 转化率 | `conversion_rate` | `buy_users / uv` | **默认按人、按天去重**；分母是访问人数，不是浏览人数 `pv_users` |
| 转化率（按次数） | `conversion_rate_by_action` | `buy_cnt / pv` | 对照口径，仅用于证明"歧义存在" |
| 加购率 | `cart_rate` | `cart_users / uv` | 分母同样是 `uv`；类目粒度用 `dws_category_daily.uv_users` |
| 加购成交率 | `cart_to_buy_rate` | `cart_buy_users / cart_users` | 严格串行口径 |
| 复购率 | `repurchase_rate` | `repurchase_users / buy_users` | |
| 次日留存率 | `d1_retention_rate` | `d1_retained_users / d0_users` | 分母是留存矩阵的 cohort 人数，不是明细表 uv |
| 7 日留存率 | `d7_retention_rate` | `d7_retained_users / d0_users` | 直接用 `d7_rate` 列，不要重算 |
| 活动日转化提升 | `promo_conversion_lift` | `(promo_rate - base_rate) / base_rate` | 基线 = 活动日前 7 天 |

## 三、最容易被追问的四个口径争议

### 争议 1：转化率按人算还是按次算？
- **默认按人**（`conversion_rate` = 购买人数 / 访问人数）。这是电商行业主流口径。
- 按次口径保留为 `conversion_rate_by_action`，**只在对照实验中使用，不与默认口径混用**。
- 语义层价值就在这里：同一个词有两种算法，配置里写清楚，模型不会自己猜。
- 这也是"无语义层 vs 有语义层"对比实验的实验材料：两组结果的差距 = 口径歧义的量化代价。

### 争议 2：成交人数 vs 成交笔数
问"多少人买"用 `buy_users`，问"多少单/多少件"用 `buy_cnt`。
"销量"这个词两种都可能指，术语表里明确要求追问或按上下文判定。

### 争议 3：加购未购是按 session 还是按天？
- 本项目**按 session × 类目**判定，因为路径表的粒度就是它。
- 代价：用户上午加购、下午购买，算作"已成交"，不计入流失。
- 若业务要"按天是否买过"的宽口径，应改用 `dws_user_daily` 的 `cart_cnt>0 AND buy_cnt=0`，两者结果不同，**不能混着讲**。

### 争议 4：大促日是哪一天？
天池 UserBehavior 实际覆盖 2017-11-25 ~ 12-03，**不含双11**。
因此：
- 大促日 = 数据集最后一天（`max_dt`），配置项 `promo_date_source: max_dt`
- 用户明确问"双11/双12/618"时 → **拒答**，并说明数据不覆盖，可改问活动日
- 绝不拿最后一天的数据冒充双11——这是事实性错误，比"不会算"更严重

### 争议 5：转化率的分母是访问人数还是浏览人数？
真实数据里两者**不相等**：约 1.78% 的成交行为没有对应的浏览记录（直接下单链接、召回唤醒等）。

| 口径 | 定义 | 真实数据（2017-12-03） |
|---|---|---|
| 访问人数 `uv` | 有任意行为（pv/cart/fav/buy）的去重用户 | 24,455 |
| 浏览人数 `pv_users` | 有 pv 行为的去重用户 | 23,696 |

本项目统一采用 **`uv`**：转化率、加购率的分母都是访问人数。
类目粒度用 `dws_category_daily.uv_users`（与全站 uv 同口径）。
合成数据上两者恰好相等，所以这个歧义**只有在真实数据上才会暴露**——
评测首轮 6 条失败中 3 条来自这里。

### 争议 6：跨天"日均值"怎么算？
问"活动日比前 7 天日均高多少"时，正确做法是**先按天聚合，再对日值求平均**：

- ✅ `AVG(每日转化率)` / `AVG(每日 UV)`
- ❌ 把 7 天人数合并后再算比率 / ❌ 7 天去重 UV ÷ 7

后者会被人数多的日期主导，且跨天去重会让多天活跃用户只计一次，系统性低估日均。
当前模型在这两类问题上稳定出错（`tm_001`、`tm_009`），已作为已知边界记录在评测报告。

## 四、维度字典（9 个）

| 维度 | biz_name | 类型 | 枚举映射（关键部分） | 注入策略 |
|---|---|---|---|---|
| 日期 | `dt` | DATE | — | 允许分组，支持日/周/月粒度 |
| 时段 | `hour` | CATEGORY | 晚上8/9/10点 → 20/21/22；黄金时段 → 20-22 | 允许分组 |
| 行为类型 | `behavior_type` | CATEGORY | 浏览/查看/逛 → pv；加购/放购物车 → cart；收藏 → fav；购买/下单 → buy | 仅过滤 |
| 类目 | `category_id` | ID | — | 允许分组（展示时替换为 `dim_category.category_name`） |
| 商品 | `item_id` | ID | — | 允许分组（无商品标题，回答需说明） |
| 会话 | `session_id` | ID | — | 仅过滤 |
| 用户 | `user_id` | ID | — | **隐藏**（缩到"按用户拆"无业务意义且行数不可控） |
| RFM 分层 | `rfm_segment` | CATEGORY | 高价值/潜力/新客/流失预警/一般 | 允许分组 |
| 是否大促日 | `is_promo_day` | CATEGORY | 1 = max_dt 当日 | 仅过滤 |

`dim_category` 目前是占位名（`类目{id}`，`name_source = placeholder`）。
回答中必须说明名称来源，不允许编造"女装/美妆"这类真实类目名。

## 五、必须拒答的问题（7 类）

来源：`metrics.yaml → no_answer`（4 条，按主题）+ `dimensions.yaml → unavailable`（6 条，按维度），去重后共 7 类。

| 类别 | 示例 | 原因 | 建议替代 |
|---|---|---|---|
| 金额类 | 退款金额、GMV、客单价、销售额 | 无金额/退款字段 | 改用成交笔数 / 成交人数 |
| 地域类 | 各省分布、华东、城市 | 无地域字段 | 改问类目或时段分布 |
| 用户属性 | 性别、年龄、会员等级、新老客标签 | 无画像字段 | — |
| 商品属性 | 品牌、价格、库存、尺码 | 仅有 category_id | — |
| 渠道 | App、小程序、H5、PC、站外 | 无来源渠道字段 | — |
| 售后与履约 | 退货率、物流时效、退款原因 | 无售后链路数据 | — |
| 具体大促日 | 双11、双12、618、年货节 | 数据仅覆盖 11-25~12-03 | 改问"活动日"（max_dt） |

拒答在 `loader.refusal_reason()` 中**确定性执行**，不经过 LLM。
理由：`no_answer` 类评测要求 100% 拒答，不能依赖模型当天是否听话。

## 六、时间解析规则

| 用户说法 | 解析结果 |
|---|---|
| 今天 / 今日 | `max_dt` |
| 昨天 / 昨日 | `max_dt - 1 天` |
| 上个月 | `max_dt` 所在月的上一自然月（数据不覆盖则拒答） |
| 去年 / 同比 | 直接拒答（数据不覆盖） |
| 前7天 / 近一周 | 相对活动日（`max_dt`）的前 7 天 |
| 大促当天 / 活动日 / 最后一天 | `max_dt` |
| 双11 / 双12 / 618 | 拒答 |

生成 SQL 前必须先解析成具体日期并回显，禁止把"昨天"直接交给模型自由发挥。

## 七、质量门槛（每次口径改动都要跑）

```bash
cd backend
python -m eval.runner --validate-only   # ① gold SQL 是否仍然合法
python -m eval.runner                   # ② 执行准确率是否退化
```

数仓侧在 `run_all.sql` 末尾自动跑 4 条一致性校验，期望全部为 0：
PV 总额一致、RFM 人数守恒、留存分母一致、无"成交但无浏览"。

## 八、数据来源与诚实声明

- 当前仓库内的 `data/ods/userbehavior_sample.csv` 为**合成数据**，仅用于验证链路，不代表任何业务结论。
- 真实数据需从天池下载（约 1 亿行），按用户抽样 500 万~1000 万行入库。
- 该数据集**无金额字段**，所有金额相关结论都不成立。
- 该数据集**不含双11**，任何"双11 表现"的说法都不成立。
- 类目名称为占位，任何具体类目结论都要等真实映射表到位后复核。
